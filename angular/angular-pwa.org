  Key PWA Configuration Options

   1. `public/manifest.webmanifest`
      This file controls how your app appears to the user when installed on their device (e.g., as a "Home Screen" app).
       * `name` & `short_name`: The titles shown on the splash screen and under the icon.
       * `icons`: Different sizes for various devices. If you change your logo, update these files in public/icons/.
       * `theme_color` & `background_color`: Define the browser UI color and the splash screen background.
       * `display`: `"standalone"`: Makes the app look like a native app (hiding the browser address bar).

   2. `ngsw-config.json`
      This is the core of your Service Worker's behavior. It determines how your app works offline.
       * `assetGroups`: Defines which static assets (HTML, JS, CSS, fonts) are cached.
           * installMode: "prefetch": Downloads all files while the user is still using the app, ensuring it's ready for offline use immediately.
       * `dataGroups`: (You can add this manually) Useful for caching API responses or external data. You can choose between freshness (try network first, then cache) or performance (cache first).

   3. `src/app/app.config.ts` (`provideServiceWorker`)
      This is where the Service Worker is registered in your code.
       * `enabled: !isDevMode()`: By default, the PWA features only run in production builds. You won't see it working with ng serve unless you change this (though testing in dev is generally discouraged as it can lead to "sticky" cached
         versions of your code).
       * `registrationStrategy`: registerWhenStable:30000 means it waits for the app to be stable (or for 30 seconds) before registering, so it doesn't slow down the initial page load.

  How to test it
  To see the PWA in action, you must run a production build:
   1. Run ng build.
   2. Serve the dist/angular-app/browser folder using a simple HTTP server (like npx http-server).
   3. Open the URL in Chrome, go to DevTools > Application > Service Workers to see it registered.

* testando localmente

✦ Yes, you absolutely can! Browsers treat localhost and 127.0.0.1 as secure contexts, which means they allow Service Workers to run even without HTTPS.

  However, by default, Angular disables the Service Worker during ng serve to prevent development code from being cached. To test it locally, you need to follow these steps:

  1. Create a Production Build
  Run the build command to generate the optimized files and the Service Worker script:
   1 ng build

  2. Serve the build folder
  You cannot just open the index.html file; you need a real web server. Use http-server (a lightweight Node.js server) to serve your dist folder:
   1 # Replace 'angular-app' with your project name if different
   2 npx http-server dist/angular-app/browser -p 8080

  3. Verify in the Browser
   1. Open http://localhost:8080 in Chrome or Edge.
   2. Install Prompt: You should see an "Install App" icon (a small computer with an arrow) in the address bar.
   3. Application Tab: Open DevTools (F12), go to the Application tab, and click Service Workers. You should see ngsw-worker.js activated and running.
   4. Offline Test: In the same Service Workers tab, check the Offline box and refresh the page. Your app should still load!

  Important Dev Tip
  When you make changes to your code, you must re-build (ng build) and refresh the browser.

  Watch out for caching: If the app seems "stuck" on an old version, go to DevTools > Application > Storage and click "Clear site data" to force the browser to fetch the new Service Worker.

   1. Generate SSH Keys:
       - Run ssh-keygen -t rsa -b 4096 -f gitlab_deploy_key.
   2. Configure GitLab:
       - Add the Public Key to your GitLab repository under Settings > Repository > Deploy Keys (Ensure "Allow write access" is checked).
   3. Configure GitHub:
       - Add the Private Key to your GitHub repository under Settings > Secrets and variables > Actions as a new repository secret named GITLAB_SSH_PRIVATE_KEY.

   - Efficiency: By pushing only the dist folder to a clean branch, you keep your GitLab repository history small and fast.

* ativar github pages
✦ The error HttpError: Not Found (Status 404) during the deployment step almost always means that GitHub Pages is not yet fully activated for your repository, or it is configured to use a different source.

  To fix this, you need to toggle a setting in the GitHub web interface:

   1. Open your browser to: https://github.com/wagnermarques/AngularStaticDashboards/settings/pages (https://github.com/wagnermarques/AngularStaticDashboards/settings/pages)
   2. Look for the Build and deployment section.
   3. Under Source, change the dropdown from "Deploy from a branch" to "GitHub Actions".
   4. Once you change this, re-run the failed action in the Actions tab.

  Why this happens:
  By default, GitHub repositories expect you to push files to a branch (like gh-pages). Since our workflow uses the modern method of uploading an "artifact" directly to the Pages infrastructure, you must explicitly tell GitHub to "listen"
  for deployments coming from Actions.

  Note: If you've already set it to "GitHub Actions" and it still fails, wait about 60 seconds for the internal GitHub API to propagate the change and try running the workflow again.
